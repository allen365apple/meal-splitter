## 一、錯誤清單（合併後，依嚴重度排序）

### 🔴 P0-1　取消所有分攤人 → 金額直接消失

- **發現者**：Codex GPT-5.6
- **驗證**：✅ Claude 實測重現
- **位置**：[index.html:234](index.html:234)（`calculation`）、[index.html:162](index.html:162)（`toggleItemSharer`）

**實測**：把「高麗菜 $100」的四位成員全部取消勾選，系統允許且無任何提示。

| | 總金額 |
|---|---|
| 取消前 | $845 |
| 取消後 | **$735** |

$100 連同服務費整整蒸發。項目仍列在清單上顯示「$100」，但一毛都沒算進去。

**為何最嚴重**：畫面看起來完全正常，不會有人發現錢不見了。

**修法**：
1. `toggleItemSharer` 取消最後一人時擋下並提示，不允許 0 人分攤；
2. 或保留「⚠️ 未分配金額 $X」區塊，明確顯示還有多少錢沒分出去；
3. 刪除成員後也要掃一次，檢查是否有菜色因此變成 0 人分攤。

建議採 1 + 3（最單純，也符合「分帳機不該讓錢消失」）。

### 🔴 P0-2　匯入千分位金額 → 金額被截斷

- **發現者**：Codex GPT-5.6
- **驗證**：✅ Claude 用程式碼裡的正規表示式實測，並發現更嚴重案例
- **位置**：[index.html:182](index.html:182)（金額正規表示式）

**實測**：

| 輸入 | 解析成 | 少收 |
|---|---|---|
| 牛排 $1,200 | 牛排 $1, → **$200** | 1,000 |
| 和牛 2,800元 | 和牛 2, → **$800** | 2,000 |
| 龍蝦 1,050 | 龍蝦 1, → **$50** | 1,000 |

「龍蝦 1,050」變成 $50。台灣帳單上千元菜色很常見，這是目前單筆金額誤差最大的錯。

**修法**：
- 解析前先正規化千分位：把 `$1,200`、`1,200 元` 一律轉成 `1200`；
- 從每行**最後一個**金額開始解析，避免品名裡的數字被當成價格；
- 搭配 P1-6 的匯入預覽，讓使用者在正式加入前看到解析結果。

### 🔴 P0-3　尾差：個人加總 ≠ 總額

- **發現者**：Claude Opus 5 與 Codex GPT-5.6（雙方獨立發現，測法與數字一致）
- **驗證**：✅ 雙方實測一致
- **位置**：[index.html:234](index.html:234)（`calculation`）、[index.html:541](index.html:541)（個人卡片顯示）

**實測**：3 人均分 $100 + 10% 服務費

| 畫面顯示 | 金額 |
|---|---|
| 總金額 | **$110** |
| 朋友 A / B / 3 | 各 $37 |
| 三人加總 | **$111** |

另一組實測（4 人、7 筆）：總額 $845，個人加總 $844。**方向不固定，有時多收有時少收。**

**修法**（採 Codex 的技術方案，比我原本的「塞給付錢的人」更正確）：
1. 全程以整數「分」計算，避免浮點誤差；
2. 先算出總額，再用**最大餘數法**分配尾差；
3. 個人明細、服務費、全員結算單全部使用同一套分配後的金額；
4. 介面標註尾差歸屬，或讓使用者指定（可與「請客功能」的付款人設定整合）。

> ⚠️ **依賴關係**：此項必須在「請客功能」之前完成。請客會重新分配金額，若尾差邏輯尚未統一，請客會再製造出第二套尾差，等於要改兩次。

### 🔴 P1-1　匯入吃掉負號：折扣 −50 變成 +50

- **發現者**：Claude Opus 5
- **驗證**：✅ 實測重現（匯入後清單顯示「折扣 $50」）
- **位置**：[index.html:182](index.html:182)、[index.html:188](index.html:188)

負號被丟棄後只剩 `50`，**折價直接變成加價**，一筆就差 100 元。

> 📌 這一項是我初次「只讀程式碼」時判斷錯誤的地方。當時我判斷「負數會被忽略，所以總額算多」，實測後才發現是被轉成正數，比原判斷嚴重。此紀錄保留，用來標示「只讀程式碼」與「實際跑過」的差別。

**修法**：偵測到負號要保留；或更好的做法是把折扣做成獨立的「折抵」欄位，不混在菜色清單裡。

### 🔴 P1-2　匯入把「服務費」當成一道菜 → 服務費收兩次

- **發現者**：Claude Opus 5（Codex 有在匯入預覽建議中順帶提到擴充排除清單，未列為獨立錯誤）
- **驗證**：✅ 實測重現
- **位置**：[index.html:183](index.html:183)（黑名單）

目前黑名單只擋「小計／總計／Total／找零／合計／TAX／電話／統編／地址／發票」，**沒擋「服務費」「清潔費」「低消」「服務料」「稅額」**。

實測：帳單上的「服務費 88」被匯入成一道 $88 的菜均分，第 3 步又整體加 10% → **服務費被收兩次還被加成**。

**修法**：
- 黑名單補上上述詞彙，並改為不分大小寫；
- 進階：辨識到「服務費 88」時，自動去推算並填入服務費率，而不是當成菜。

### 🔴 P1-3　匯入砍掉菜名裡的「元」字

- **發現者**：Claude Opus 5
- **驗證**：✅ 實測重現（「元盅雞湯 180」→「盅雞湯 $180」）
- **位置**：[index.html:181](index.html:181)

為了清掉「180元」的「元」用了全域替換，菜名裡的「元」也被砍。「元氣豬排」會變「氣豬排」。

**修法**：只清掉金額結尾的「元／圓」，不要動品名。

### 🔴 P1-4　中途加人 → 顯示「大家都有」但新人沒被算進去

- **發現者**：Claude Opus 5
- **驗證**：✅ 實測重現
- **位置**：[index.html:127](index.html:127)（`addUser`）

**實測**：先輸入菜 → 回上一步新增「朋友 4」→ 回到第 2 步：

- 「高麗菜」的「全選」按鈕**仍是亮綠色**（看起來大家都有），但朋友 4 是灰的 → **畫面在騙人**
- 結算時朋友 4 = **$184**，其他三人 $220
- 上方「這道菜誰有吃」還停在 **「3 人分攤」**，朋友 4 未被自動勾選 → **之後新輸入的每一道菜也都會繼續漏掉他**

最後一點最嚴重：這不是單筆錯誤，是會一直錯下去。

**修法**：
1. `addUser` 時，把標記為「大家都有」的既有項目同步加入新成員；
2. 同時把新成員補進當前的 `currentSharers`；
3. 或反過來：「大家都有」不要存成固定名單，改成動態解析（推薦，一勞永逸）。

### 🔴 P1-5　金額欄位允許 0 與負數

- **發現者**：Codex GPT-5.6
- **驗證**：✅ Claude 實測重現（品名 `TestZero`、金額 `0`，「加入清單」為可按狀態）
- **位置**：[index.html:134](index.html:134)（`addItem`）

成因：程式只檢查「字串是不是空的」，而 `"0"` 不是空字串。

**修法**：金額必須是有限數字且大於 0；輸入欄加 `min`／`step`；`addItem` 內再驗一次，不能只靠 HTML 限制。計算機也要處理除以 0、無限大與非數字結果。

### 🟡 P1-6　「已複製」可能是騙人的

- **發現者**：Codex GPT-5.6
- **驗證**：✅ 讀程式碼確認（`document.execCommand('copy')` 的回傳值未檢查，一律呼叫成功回呼）
- **位置**：[index.html:235](index.html:235)（`executeCopy`）

複製失敗也照樣顯示「已複製」。分帳的最後一步就是複製貼群組，這裡失敗而使用者不知道，體驗很差。

**修法**：優先用 `navigator.clipboard.writeText()`，失敗才走舊方法；只有確實成功才顯示成功狀態。

### 🟡 P2-1　重新整理資料全失

- **發現者**：Claude Opus 5 與 Codex GPT-5.6（雙方皆發現）
- **驗證**：⚠️ 讀程式碼確認「確實沒有任何存檔機制」（搜過 `localStorage`，零筆），未在瀏覽器實際重現資料消失

**設計上的自我矛盾**：主打功能是「拍帳單 → 切去 ChatGPT 轉文字 → 貼回來」，但手機切 App 回來若被系統清掉背景，整頁就是白紙。

**修法**：`localStorage` 自動暫存；加「新增一桌／清空目前帳單」按鈕（現在想清空只能重新整理）；進階可做 JSON 匯出／匯入。

### 🟡 P2-2　標題列滑動時遮住輸入欄

- **發現者**：Claude Opus 5

### 🟢 P2-8　不是完整 PWA

- **發現者**：Claude Opus 5 與 Codex GPT-5.6（雙方皆發現）

有加入主畫面說明與 Apple touch icon，但沒有 `manifest`，也沒有 service worker。Android 不會出現真正的「安裝應用程式」，也無法離線使用——跟安裝教學的文案不一致。

**修法**：補 `manifest.webmanifest`、完整 icon、service worker 與離線快取；若暫不做，先把文案改成「加入主畫面捷徑」。

### 🟢 P2-9　正式環境使用即時 CDN 編譯

- **發現者**：Claude Opus 5（白屏風險）＋ Codex GPT-5.6（console warning、建議預先建置）
- **位置**：[index.html:18](index.html:18)、[index.html:23](index.html:23)

**修法**：預先編譯 JSX 與 Tailwind，鎖定或自行託管必要資源；至少加一個載入失敗的提示畫面。

## 三、新功能規格

### ⭐ 新功能 A：批次卡片檢視（逐筆確認）

#### 需求
手動一筆一筆輸入維持原樣。但走「貼上文字明細 → 開始匯入」時，目前全部預設「大家都有」，還要自己回去一筆一筆點誰吃，很累。改為匯入後進入卡片模式：一道菜一張卡，確認完換下一張；底部要有小按鈕可直接略過、回到全部清單。

#### 觸發條件
- ✅ 走 `handleBatchImport`（批次匯入）→ 進入卡片模式
- ❌ 走 `addItem`（手動單筆）→ 維持現狀，不進卡片模式

#### 流程
```
貼上明細 → 開始匯入 → 解析
                         ↓
            ┌─── 卡片檢視模式（全螢幕）────┐
            │  進度 3 / 12                │
            │                             │
            │  宮保雞丁          $180  ✎  │  ← 品名、金額可直接改
            │  ───────────────────────    │
            │  [全選] [😋一般] [🥦吃素]    │  ← 標籤快捷
            │                             │
            │  [朋友A] [朋友B] [朋友3]     │  ← 大格子點選（預設全選）
            │  [朋友4]                    │
            │                             │
            │  [← 上一道]  [確認，下一道 →] │
            │                             │
            │  略過檢視，直接看全部清單     │  ← 小字按鈕
            └─────────────────────────────┘
                         ↓
              最後一張 →「完成」→ 回全部清單
```

#### 設計決策與理由

1. **預設維持全選（大家都有）**
   使用者只需「點掉沒吃的人」，比從零開始勾快得多。聚餐現實是多數菜大家都有吃。
2. **卡片上要能改品名與金額**
   吸收 Codex 的匯入預覽建議。匯入解析錯誤（千分位、菜名被砍）在這裡就能當場修掉，是 P0-2／P1-3 的第二道防線。
3. **要有「上一道」**
   點錯了不用整個重來。
4. **略過按鈕的行為**
   已確認的卡片保留其設定，未確認的維持「大家都有」，直接回清單。
5. **顯示被忽略的行數**

#### 邊界情況（要處理）
1. **防循環**：一個人只能是「被請」或「請客者」其中一種，不能同時是。A 請 B、B 又請 C 的情形直接擋掉。

3. **不能全部人都被請**：至少要留一個付錢的，否則帳單沒人付。
4. **請客者被刪除**：若某筆請客的所有 payer 都被刪光，自動取消該筆請客並提示。
5. **被請者被刪除**：自動移除該筆請客。
6. **請客金額除不盡**：尾差跟著主邏輯一起分，不另做一套。
7. **結算單文字輸出**要反映請客關係，例如：

**震動問題的成因與解法**：

單一門檻（`scrollY > 20`）造成回饋迴圈——縮小 → 版面變短 → 瀏覽器把 `scrollY` 往回夾 → 掉到門檻以下 → 展開 → 版面變長 → 又超過門檻 → 縮小，無限來回。

實測可見夾動幅度很大：要求捲到 y=145，縮小後實際 `scrollY` 被夾到 **11**。舊門檻 20 正好落在這個區間裡，所以會抖。

三層解法：
1. **雙門檻（hysteresis）**：往下超過 140 才縮，但只有回到最頂端（< 8）才展開。縮小造成的夾動只會讓 `scrollY` 變小，碰不到展開條件，迴圈就斷了。
2. **切換後 350ms 冷卻**：等版面高度與夾動完全結束再重新判斷，處理極端視窗尺寸下的殘餘情況。
3. **`requestAnimationFrame` 節流 + ref 比對**：避免每個捲動事件都觸發 re-render。

**實作時修掉的額外問題**：compact 模式的展開鈕原本寫在一個 `max-h-0 opacity-0 overflow-hidden` 的容器裡，所以縮小後那顆鈕看不到也點不到。已移到永遠可見的標籤列右側，並加上目前人數（例如「3人 ⌄」）。

**過程中我自己製造又修掉的 bug**：`addUser` 補進 `currentSharers` 時，會在第 2 步初始化之前就先塞值，導致「預設全選」判斷失效（實測顯示「2 人分攤」而非 4）。已改成只有在已初始化時才追加。

**設計決策**：

1. **放在第 3 步結算頁**（規劃時已確認）。請客是結算時的決定，不污染第 2 步「誰吃了什麼」的事實。
2. **彈窗顯示代價**：「{name} 這餐是 $X」＋「N 人一起請 → 每人多付 $Y」，按下去之前就看得到要付多少。
3. **防連鎖採「自動重新指派」而非禁止**：若某人已在幫別人出錢、後來自己也被請，系統會自動把他從原本的請客者名單移除，該筆請客由剩下的人承擔。比直接禁止更符合實際使用（「算了，你也不用出了」）。計算端另有一層守門，不依賴狀態正確性。
4. **整數化只在「要付錢的人」之間分配**，被請的人保證是 0，不會因為最大餘數法分到 $1。
5. **`splitExact()` 統一所有顯示拆解**：總額 → 自己這份／各筆代付 → 餐費／服務費／固定加收 → 明細各行，四層全部用同一個函式，每層加總都完全相符，且可正確處理負數。

| 第 2 步 | 獨立的「怎麼輸入菜色？」畫面 ✅ |
| compact 窗格高度 | **459px → 112px**（縮小 347px，原本含標籤列約 180px）✅ |
| compact 內容 | 只剩「品項＋金額＋計算機」「加入清單＋2人 ⌄」兩列 ✅ |
| 點品項欄 | 展開回 459px，標籤列與九宮格出現 ✅ |
| 展開後連續滑動 | **保持展開**，不會被收回 ✅ |
| 加入一筆後再滑 | 正常收起回 112px ✅ |
| 捲回頂端 | 展開 ✅ |
| 手動 7 道 → 上一步 → 改選大量匯入 | 菜色**完整保留**，匯入 2 筆後共 9 道，卡片檢視只跑新的 2 筆（1/2）✅ |
| 第 4 步結算 | 餐費 980 → 總額 1078，每人 539+539 = **1078** ✅ |

> 測試插曲：驗收時我把預期餐費算成 920（漏掉測試中重複加入的一筆魯肉飯），一度誤判為失敗。實際讀出九筆項目後確認餐費是 980、總額 1078，程式計算正確。

**另一個測試環境限制**：自動化環境用 `.focus()` 不會觸發 `focus` 事件（視窗未取得焦點時瀏覽器不派送），所以「點輸入欄就展開」一開始測起來像壞的。改用 `focusin` 事件驗證後確認功能正常。這類「測不到不等於壞掉」的情況值得記住。

## 五之五、階段 10：份數權重 ＋ CDN 版本鎖定 ✅ 已完成 2026-09-15

原本列在「已知限制」裡的兩項，其中可以安全處理的部分做掉了。

### 份數權重（一個人吃兩份不用把菜輸入兩次）

**資料模型**：`item.units = { [userId]: n }`，沒設定的人就是 1 份。向後相容——舊存檔沒有 `units` 欄位，一律當成每人 1 份。

**計算**：直接餵給既有的 `allocate()`（它本來就支援權重），所以最大餘數法與四層加總相符的保證全部沿用，不需要另寫一套。

**介面**：
- 每張菜色卡片右上角一顆「⚖️」；有人吃多份時會變藍並顯示總份數（例如「⚖️ 5份」）
- 點開是份數面板，列出目前分攤的人＋ −／+ 步進器，標題即時顯示「$200 ÷ 5 份 = 每份 $40」
- 分攤人 chip 上會標記「朋友 A ×3」
- 逐筆卡片檢視裡也有「⚖️ 份數」入口
- 份數限制 1～20 份

**顯示規則**：份數都是 1 時維持「÷ 3人」，有人多份時改成「÷ 5份 ×3」，不會干擾原本最常見的情況。

**驗收結果**（2026-09-15，於 `http://localhost` 實測）：

測試情境：3 人、炒飯 $300（各 1 份）、啤酒 $200（朋友 A 3 份、其餘各 1 份，共 5 份）

### CDN 版本鎖定

原本用 `react@18` 這種版本範圍，某個小版本出問題就會整頁空白、而且無從得知是哪一版。已改為：

| 資源 | 改動 |
|---|---|
| React | `unpkg react@18` → `cdnjs react/18.3.1`（確切版本） |
| React DOM | `unpkg react-dom@18` → `cdnjs react-dom/18.3.1` |
| Babel Standalone | `unpkg @babel/standalone`（無版本） → `cdnjs babel-standalone/7.26.4` |
| Tailwind | 維持 `cdn.tailwindcss.com`（play CDN 無 cdnjs 版本） |

三個網址都實測 HTTP 200，頁面載入正常無錯誤。

> **仍未做**：多 CDN 自動備援。一個 CDN 掛掉時自動改從另一個載入，需要串接式的載入邏輯，複雜度與出錯風險都不低。目前的防線是既有的「4 秒後仍空白就顯示載入失敗＋重新載入鈕」。

### 仍然沒做（且建議先不要做）

| 項目 | 為什麼先不做 |
|---|---|
| 預先編譯（消除首次白屏） | 需要建置流程，會失去「單檔傳給朋友就能用」這個最大優點 |
| 拆檔 | 同上。目前 1,598 行雖然長，但單檔好備份、好傳遞 |

這兩項都是「為了效能犧牲可攜性」的取捨，屬於使用者的決定，不該由我單方面改掉。

### 金額正確性的保證

所有金額都以整數「分」計算，顯示層用 `splitExact()` 做四層最大餘數法分配：

```
明細各行加總  =  餐費小計
餐費小計 + 服務費 + 固定加收  =  自己這份
自己這份 + 各筆代付  =  應付總額
所有人的應付總額加總  =  畫面總金額
```

每一層都完全相符，且每一行與真實值的差距不超過 1 元（實測最大 0.67）。
